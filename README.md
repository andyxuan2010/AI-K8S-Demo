# AIonK8sDemo
The task is to deploy the large language model “Dolly v2 3b” as an API on the Kubernetes cluster

## Summary
Databricks' dolly-v2-3b, an instruction-following large language model trained on the Databricks machine learning platform that is licensed for commercial use. Based on pythia-2.8b, Dolly is trained on ~15k instruction/response fine tuning records databricks-dolly-15k generated by Databricks employees in capability domains from the InstructGPT paper, including brainstorming, classification, closed QA, generation, information extraction, open QA and summarization. dolly-v2-3b is not a state-of-the-art model, but does exhibit surprisingly high quality instruction following behavior not characteristic of the foundation model on which it is based.

## Model Overview
dolly-v2-3b is a 2.8 billion parameter causal language model created by Databricks that is derived from EleutherAI's Pythia-2.8b and fine-tuned on a ~15K record instruction corpus generated by Databricks employees and released under a permissive license (CC-BY-SA)

## Shell scripts

Repository shell scripts use Bash strict mode, version `1.1.0`, timestamped output,
and an error trap that reports the failing line and exit status. Standard script
output and errors are appended to `~/.local/state/ai-k8s-demo/logs/` (or the
equivalent path under `XDG_STATE_HOME`). Set `SCRIPT_LOG_DIR` to choose another
log directory. The Linux VM bootstrap supports Ubuntu and Red Hat family distributions
and logs to `/var/log/aks-vm-bootstrap.log`; set `BOOTSTRAP_LOG_FILE` to override it.

Scripts in `scripts/` share logging and error helpers from `scripts/lib/common.sh`.
The bootstrap script is self-contained because Terraform passes it to the VM as
custom data. The older deployment entry point is `k8s/run.sh`.

Each executable script has a header with its version, summary, usage, and inputs.
AKS scripts support `--help`, reject unexpected positional arguments, validate
common environment values before running commands, and report failures with the
script name, source line, and exit status. Set `SCRIPT_LOG_DIR` to redirect their
combined timestamped output.

Additional AKS operations scripts:

- `aks-preflight-check.sh` validates cluster access and server-side checks the Kubernetes manifests.
- `aks-api-logs.sh` follows or displays recent Dolly API logs (`FOLLOW=false` disables following).
- `aks-watch-pods.sh` watches pods in `K8S_NAMESPACE`; set `POD_SELECTOR` to filter them.
- `aks-events.sh` displays recent namespace events (`EVENT_LIMIT` sets the number shown).
- `aks-rollout-history.sh` displays deployment rollout revisions and details.
- `aks-rollback-api.sh` rolls the Dolly API deployment back, optionally to a specified revision.
- `aks-update-api-image.sh` updates a deployment image and waits for rollout completion.
- `aks-port-forward-api.sh` forwards a local port to the Dolly API service.
- `aks-ingress-logs.sh` follows or displays ingress controller logs.
- `aks-resource-usage.sh` displays node, pod, and HPA resource information; metrics-server is required for `kubectl top`.

All AKS operation scripts accept `K8S_NAMESPACE` (the ingress log script also accepts
`INGRESS_NAMESPACE`). They require `kubectl` and a configured context with the relevant
cluster permissions.

The environment tfvars file selects Ubuntu by default. Set `vm_os_family = "redhat"`
to use the configured Azure Marketplace RHEL 9 Gen2 image. Terraform passes the
AKS cluster version to the bootstrap so its `kubectl` client matches the cluster
minor version.

The root `main.tf` composes the shared resource group, VNet/subnet, NSG, and AKS
modules from `andyxuan2010/azure-template`. The jumpbox stays as root resources
because the template Linux VM module depends on shared Key Vault and storage
resources that this demo does not provision. Resource inputs are kept in each
environment's `terraform.tfvars`; variable declarations remain in `variables.tf`.

## Terraform environments

The dev environment follows the repository's environment-file layout:

- `environments/dev/backend.hcl` contains the Azure Storage backend settings.
- `environments/dev/terraform.tfvars` contains the dev environment inputs.
- Only dev currently has a populated environment variable file. Add a matching
  `terraform.tfvars` under another environment directory before planning there.

Terraform backend settings cannot be supplied through ordinary input variables,
so initialize with the backend file and supply the variable file to plan/apply:

```bash
terraform init -reconfigure -backend-config="environments/dev/backend.hcl"
terraform plan -var-file="environments/dev/terraform.tfvars"
terraform apply -var-file="environments/dev/terraform.tfvars"
```

Replace `network_security_rules.SSH.source_address_prefix` in the environment
tfvars with a trusted public IPv4 CIDR (`/24` or narrower, preferably your public
IP with `/32`) before planning. The checked-in public SSH keys are public key material; do not
put private keys or Azure credentials in the tfvars file. Provider versions are
recorded in `.terraform.lock.hcl`.

DNS integration is disabled for dev because the previous `argentiacapital.com`
Azure DNS zone is unavailable. With `dns_zone.enabled = false`, Terraform skips
the zone lookup and DNS record resources, and DNS-related outputs are `null`. To
use a replacement zone, set `dns_zone.enabled = true` and fill in its existing
zone name, resource group, and the three DNS A-record IPv4 targets in the dev
tfvars file. Disabling DNS will remove any DNS records still managed in Terraform
state on the next apply.
